## 🚨 CRITICAL RULES (Read First)

### Rule 1: DRY - Don't Repeat Yourself

**Before writing code, ask:**
1. Does this logic exist elsewhere? → Search `internal/pkg/` first
2. Will 2+ domains use it? → Extract to `internal/pkg/<category>/`
3. Am I copy-pasting? → 🛑 STOP. Extract to function/utility

**⚠️ CRITICAL: Domain layer CANNOT import `internal/pkg/`**
- Domain imports ONLY standard lib (`errors`, `strings`, `time`, `fmt`, `path/filepath`)
- `internal/pkg/` is for APPLICATION/INFRASTRUCTURE shared utilities, not domain

**Common violations:**
- ❌ Duplicate validation → Keep in domain entity/service (DRY in same domain OK)
- ❌ Same string logic → Extract to `internal/pkg/stringutil/` (non-domain code)
- ❌ `internal/pkg/` with I/O → Move to infrastructure layer instead

### Rule 2: Layer Boundaries (NEVER VIOLATE)

**Domain** (`internal/domain/`): ✅ Standard lib only | ❌ NO Gin, DB drivers, FFmpeg  
**Infrastructure** (`internal/infrastructure/`): ✅ Implements domain interfaces | ✅ sqlc, FFmpeg allowed  
**Application** (`internal/application/`): ✅ Orchestrates use cases | ❌ NO HTTP or DB  
**Interfaces** (`internal/interfaces/`): ✅ Gin handlers | ✅ Uses application layer

**Dependency flow**: `Interfaces → Application → Domain ← Infrastructure`

### Rule 3: Dual Database Support

ALWAYS support SQLite (default) + PostgreSQL:
- Use `sqlc` with build tags: `//go:build sqlite` / `//go:build postgres`
- Separate query files: `library.sql` (SQLite `?`) vs `library_postgres.sql` (PostgreSQL `$1`)

### Rule 4: Documentation

❌ NEVER create: CHANGES.md, SUMMARY.md, PROGRESS.md, task summaries
✅ ALWAYS update: `docs/PROJECT_PLAN.md` (mark tasks), code comments, existing docs

### Rule 5: NO Adapters or Wrappers

**CRITICAL: Adapter files are lazy and create tech debt**

❌ **NEVER create:**
- "Adapter" files (e.g., `usecases.go` that wraps individual use cases)
- "Facade" structs that just call other structs
- Wrapper methods that add zero value
- Bridge patterns between layers that don't transform data

✅ **INSTEAD:**
- HTTP handlers call use cases DIRECTLY
- Each use case is a standalone struct with `Execute()` method
- If signatures don't match, FIX the existing code (update use case or handler)
- True adapters only exist for external dependencies (e.g., DB driver → Repository interface)

**Example of what NOT to do:**
```go
// ❌ BAD - Lazy wrapper adding tech debt
type UseCases struct {
    createLib *CreateLibraryUseCase
    updateLib *UpdateLibraryUseCase
}
func (uc *UseCases) CreateLibrary(...) { return uc.createLib.Execute(...) }
```

**Example of what TO do:**
```go
// ✅ GOOD - Handler directly uses use cases
type LibraryHandler struct {
    createLibrary *CreateLibraryUseCase
    updateLibrary *UpdateLibraryUseCase
}
```

## Quick Reference

### File Placement

| What | Where |
|------|-------|
| Entity | `internal/domain/<entity>/entity.go` |
| Repository interface | `internal/domain/<entity>/repository.go` |
| Domain service | `internal/domain/<entity>/service.go` |
| Domain errors | `internal/domain/<entity>/errors.go` |
| Repo implementation | `internal/infrastructure/persistence/<entity>/repository.go` |
| SQL queries | `internal/infrastructure/persistence/<entity>/queries/<table>.sql` |
| Shared utilities | `internal/pkg/<category>/` |
| Use case | `internal/application/<entity>/use_case.go` |
| HTTP handler | `internal/interfaces/http/<entity>/handler.go` |
| Tests | Same package, `*_test.go` suffix |

### Key Patterns

**Repository:**
```go
// 1. Domain interface
type LibraryRepository interface {
    Create(ctx context.Context, lib *Library) error
}

// 2. Infrastructure impl
type repo struct { queries *db.Queries }

// 3. Inject in main.go
repo := persistence.NewLibraryRepository(db)
service := library.NewService(repo)
```

**Errors:**
```go
// Domain errors
var ErrLibraryNotFound = errors.New("library not found")

// Wrap with context
return fmt.Errorf("failed to create: %w", err)
```

**Testing:**
```go
func TestEntity_IsValid(t *testing.T) {
    tests := []struct {
        name string
        entity Entity
        wantErr error
    }{{ name: "valid", entity: Entity{...}, wantErr: nil }}
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if err := tt.entity.IsValid(); err != tt.wantErr {
                t.Errorf("got %v, want %v", err, tt.wantErr)
            }
        })
    }
}
```

## Domain Layer Rules

**Structure per entity:**
```
internal/domain/<entity>/
├── entity.go      # Business object + validation
├── types.go       # Enums, value objects
├── errors.go      # var Err... = errors.New(...)
├── repository.go  # Interface only
├── service.go     # Complex business logic
└── *_test.go
```

**Allowed imports:** `errors`, `strings`, `time`, `fmt`, `path/filepath` - standard lib only  
**Forbidden:** Gin, database/sql, sqlc, FFmpeg, any external package

## Infrastructure Layer

**Structure:**
```
internal/infrastructure/
├── persistence/<entity>/
│   ├── repository.go           # Implements domain interface
│   └── queries/
│       ├── <table>.sql         # SQLite (?)
│       └── <table>_postgres.sql # PostgreSQL ($1)
```

## Development Workflow

### Critical: Vertical Slice Development

**ALWAYS complete features vertically (all layers) before moving to next feature.**

❌ **NEVER do horizontal layering** (all entities in domain, then all repos, then all use cases)
✅ **ALWAYS use vertical slices** (one feature: domain → infrastructure → application → API)

**Why?** Horizontal layering creates incomplete implementations that break at runtime.

### Definition of Done Checklist

Before marking ANY feature complete, verify ALL 8 items:

- [ ] **1. Domain entity** created with validation (`IsValid()` method)
- [ ] **2. Repository interface** defined in domain layer
- [ ] **3. Repository implementation** with ALL fields mapped (no `sql.NullString{}` placeholders)
- [ ] **4. Database migration** created and tested (both SQLite + Postgres if applicable)
- [ ] **5. SQL queries** written and sqlc generated (`make sqlc-generate`)
- [ ] **6. Integration test** written and passing (see template below)
- [ ] **7. API endpoint** implemented and tested via curl/Postman
- [ ] **8. Audit clean** - run `make audit` to catch incomplete implementations

### Creating a Feature (Example: Media Metadata)

**Step 1: Domain Layer**
```go
// internal/domain/media/entity.go

    ID         int64
    Title      string
    FilePath   string
    VideoCodec string  // ← Must be in domain model
    AudioCodec string  // ← Must be in domain model
    Width      int
    Height     int
}

// internal/domain/media/metadata.go - Business logic
func CalculateAspectRatio(width, height int) string {
    // Domain calculation logic here
}
```

**Step 2: Infrastructure - Database**
```sql
-- migrations/000004_add_audio_codec.up.sql
ALTER TABLE media ADD COLUMN audio_codec TEXT;

-- internal/infrastructure/database/queries/sqlite/media.sql
-- name: CreateMedia :one
INSERT INTO media (
    title, file_path, video_codec, audio_codec, width, height
) VALUES (?, ?, ?, ?, ?, ?) RETURNING *;
```

**Step 3: Infrastructure - Repository**
```go
// internal/infrastructure/persistence/media/repository.go
func (r *repository) Create(ctx context.Context, m *domain.Media) error {
    result, err := r.queries.CreateMedia(ctx, sqlc.CreateMediaParams{
        Title:      m.Title,
        FilePath:   m.FilePath,
        Codec:      common.NullString(m.VideoCodec), // ✅ Map actual field
        AudioCodec: common.NullString(m.AudioCodec), // ✅ NOT sql.NullString{}
        Width:      sql.NullInt64{Int64: int64(m.Width), Valid: m.Width != 0},
        Height:     sql.NullInt64{Int64: int64(m.Height), Valid: m.Height != 0},
    })
    // ... handle result
}
```

**Step 4: Application Layer**
```go
// internal/application/media/create_media.go
type CreateMediaUseCase struct {
    repo domain.MediaRepository
}

func (uc *CreateMediaUseCase) Execute(ctx context.Context, req CreateMediaRequest) (*MediaResponse, error) {
    media := &domain.Media{
        Title:      req.Title,
        FilePath:   req.FilePath,
        VideoCodec: req.VideoCodec, // ✅ Pass through from scanner
        AudioCodec: req.AudioCodec, // ✅ Pass through from scanner
    }

    if err := uc.repo.Create(ctx, media); err != nil {
        return nil, err
    }
    return toResponse(media), nil
}
```

**Step 5: Integration Test**
```go
// internal/infrastructure/persistence/media/repository_test.go
func TestRepository_Create_WithFFmpegMetadata(t *testing.T) {
```

### Anti-Patterns to Avoid

**🚨 CRITICAL: These patterns indicate incomplete implementations:**

#### 1. Empty Null Assignments
```go
// ❌ BAD - Hard-coded empty values
AspectRatio: sql.NullString{},
Codec:       sql.NullString{},
AudioCodec:  sql.NullString{},

// ✅ GOOD - Map actual data
AspectRatio: common.NullString(media.CalculateAspectRatio(m.Width, m.Height)),
Codec:       common.NullString(m.VideoCodec),
AudioCodec:  common.NullString(m.AudioCodec),
```

#### 2. No-Op Repository Methods
```go
// ❌ BAD - Method exists but does nothing
func (r *repository) Create(ctx context.Context, m *Media) error {
    return nil  // ← Feature incomplete!
}

// ✅ GOOD - Actually implements the feature
func (r *repository) Create(ctx context.Context, m *Media) error {
    _, err := r.queries.CreateMedia(ctx, /* map all fields */)
    return err
}
```

#### 3. Missing Database Columns
```go
// ❌ BAD - Domain has field, database doesn't
type Media struct {
    AudioCodec string  // ← Field exists in struct
}
// But no audio_codec column in database!

// ✅ GOOD - Create migration FIRST, then add field
// 1. migrations/000004_add_audio_codec.up.sql
// 2. Update queries/*.sql
// 3. make sqlc-generate
// 4. Add field to domain entity
```

#### 4. TODOs in Repository Layer
```go
// ❌ BAD - TODO means feature incomplete
FileHash: sql.NullString{}, // TODO: Add Hash field

// ✅ GOOD - Either implement it or document why it's missing
// If FFmpeg doesn't extract this field yet:
// Leave out of domain.Media entirely (don't add field)
// Add to backlog: "Implement file hashing in scanner"
```

#### 5. Ignoring Test Failures
```bash
# ❌ BAD
go test ./...  # 3 tests fail
git commit -m "Add media feature"  # ← Incomplete!

# ✅ GOOD
go test ./...  # All pass
make audit     # 0 issues
git commit -m "Add complete media metadata handling"
```

## TypeScript/React Coding Style

### Function Declarations

**ALWAYS use const arrow functions** (fat arrow syntax):

```typescript
// ✅ CORRECT
const MyComponent = ({ prop }: Props) => {
  return <div>{prop}</div>
}

const handleClick = () => {
  console.log('clicked')
}

// ❌ WRONG
function MyComponent({ prop }: Props) {
  return <div>{prop}</div>
}

function handleClick() {
  console.log('clicked')
}
```

**Exception**: Type definitions and interfaces use `interface` keyword

### Export Organization

**ALWAYS put exports at the end of the file**:

```typescript
// ✅ CORRECT
const MyComponent = ({ title }: Props) => {
  return <h1>{title}</h1>
}

const HelperFunction = () => {
  // ...
}

// All exports at the end
export { MyComponent, HelperFunction }
export type { Props }

// ❌ WRONG
export const MyComponent = ({ title }: Props) => {
  return <h1>{title}</h1>
}

export const HelperFunction = () => {
  // ...
}
```

**Exception**:

- Default exports can remain inline for single-component files
- Type-only exports can be inline: `export type Props = {...}`

### Type Files Convention

**ALWAYS use `*.types.ts` files for type definitions**:

```typescript
// ✅ CORRECT - ComponentName.types.ts
interface ComponentNameProps {
  title: string
  onAction: () => void
}

interface InternalType {
  id: number
}

export type { ComponentNameProps }
// Internal types can stay unexported

// ✅ CORRECT - ComponentName.tsx
import type { ComponentNameProps } from './ComponentName.types'

const ComponentName = ({ title, onAction }: ComponentNameProps) => {
  return <div>{title}</div>
}

export { ComponentName }
export type { ComponentNameProps } from './ComponentName.types'

// ❌ WRONG - Types inline in component file
interface ComponentNameProps {
  title: string
}

const ComponentName = ({ title }: ComponentNameProps) => {
  return <div>{title}</div>
}
```

**Benefits**:

1. **Separation of concerns**: Types separated from implementation
2. **Reusability**: Types can be imported without component code
3. **Clarity**: Clear API surface for each component
4. **Consistency**: Standard pattern across all components

### Component File Structure

Standard order for component files:

1. Imports (including type imports)
2. Constants/helpers
3. Main component(s)
4. Sub-components
5. Utility functions
6. Exports (at the very end, including re-exported types)

```typescript
// 1. Imports
import { useState } from 'react'
import { Button } from '@/components/ui'
import type { ComponentProps } from './Component.types'

// 2. Constants
const DEFAULT_VALUE = 'default'

// 3. Main component
const MyComponent = ({ title }: ComponentProps) => {
  return <div>{title}</div>
}

// 4. Sub-components
const SubComponent = () => {
  return <span>sub</span>
}

// 5. Utilities
const helperFn = () => {
  return true
}

// 6. Exports (END OF FILE)
export { MyComponent, SubComponent }
export type { ComponentProps } from './Component.types'
```

### Why This Style?

1. **Consistency**: Same pattern across all files
2. **Readability**: Clear separation of declarations and exports
3. **Tree-shaking**: Better bundler optimization with explicit exports
4. **Refactoring**: Easy to see what's exported vs internal
5. **Modern Standard**: Aligns with module best practices
